Türwache Dokumentation

Türwache ist ein privater Kameraserver für Ring und Netzwerkkameras. Die Weboberfläche bündelt Clips, Zeitstrahl, lokale KI und Benachrichtigungen. Wähle Deutsch oder Englisch in der Kopfzeile.

Ehrlicher Entwicklungsstand

Windows und die eigene Ring Battery Doorbell Pro wurden praktisch getestet. Livebild und neue Aufnahmen enthalten Ton, sofern die Kamera ihn liefert. Der private Kameratest funktionierte ohne Ring-Abo und laut Nutzer ohne Probeabo. Das ist keine Garantie für jedes Ring-Gerät oder eine dauerhafte, offiziell zugesicherte API-Funktion.

Ring-Konto, Internet und Ring-Cloud bleiben nötig. Das Projekt ersetzt weder die Firmware noch den Cloud-Verbindungsaufbau der Kamera. Ein Akku-Gerät wacht erst auf: Der Beginn eines Ereignisses kann fehlen. Mehrere Kameras können gleichzeitig aufnehmen; pro Kamera teilen Livebild und Aufnahme eine Verbindung. Das Gesamtlimit steht unter Betrieb.

Der Linux-x86_64-Container wurde einschließlich HTTP-Server, Modelldownload und dauerhaftem Python-Worker getestet. Echte Raspberry-Pi-Hardware, systemd-Dienstbetrieb und iOS-Installation sind noch nicht getestet. KI kann Ereignisse falsch beschreiben oder Personen übersehen. Es gibt keine Zusage von 100 % Sicherheit oder Erkennungsgenauigkeit.

Windows installieren

Voraussetzungen

Windows 10/11, Node.js 24 LTS und bei lokaler Bildanalyse Python 3.12 (64 Bit). Node 22 wird ebenfalls unterstützt; Node 26 ist für diese Version nicht freigegeben. Installer laden keine beliebigen Systemprogramme herunter und öffnen keine Firewall-Ports.

  • Offizielles Node.js
  • Offizielles Python

Installieren und starten

Privates Repository klonen oder den bereinigten Quellordner verwenden. PowerShell im Projekt öffnen. Der Ordner sollte dem normalen Benutzer gehören. Nicht als Administrator betreiben.


powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Install-Windows.ps1 -WithAI -CheckOnly
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Install-Windows.ps1 -WithAI
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-Tuerwache.ps1

Ohne lokale Personen-/Gesichtserkennung -WithAI weglassen. Die Installation lädt exakt die npm-Lockdatei, FFmpeg, die Python-Pakete und bei -WithAI drei per SHA256 geprüfte OpenCV-Modelle. Sie startet keinen Server. CheckOnly prüft Voraussetzungen ohne Downloads oder Änderungen.

Anschließend Türwache öffnen: erstes Türwache-Admin-Konto anlegen, danach das Ring-Konto verbinden und dessen Bestätigungscode eingeben. Passwörter nur in die eigene lokale App eingeben.

Konfiguration und Start

Optional .env.example nach .env kopieren. Die neuen Startskripte laden diese Datei. npm start allein lädt sie nicht. .venv/Scripts/python.exe wird automatisch ausgewählt, sofern AI_PYTHON nicht gesetzt ist. Eine vorhandene .env-Einstellung hat Vorrang vor dieser Vorauswahl, soweit keine Prozessvariable gesetzt ist.

Der Doppelklick auf Start-Tuerwache.cmd nutzt denselben Starter. Das Fenster offen lassen; mit Strg+C sauber stoppen. Bei einem Update zuerst stoppen und ein Backup anlegen. Kein zweites Exemplar gegen dieselbe Datenablage starten.

Gesichts-Worker auf demselben Windows-PC

Die Gesichts-Engine Lokal auf Türwache verwendet SFace direkt. Über den Worker kannst du auch ArcFace nutzen. Dafür müssen Python und die OpenCV-Modelle eingerichtet sein, wie unter Installieren und starten beschrieben.

Automatisch mit Türwache starten

Wähle unter KI-Anbieter → Gesichts-Worker die Option Automatisch auf diesem Gerät. Lass ArcFace für Kameras freigeben für den ersten SFace-Test aus. Prüfe die Verbindung, schalte Gesichts-Worker freigeben ein und speichere. Bei jedem Türwache-Start läuft der integrierte Worker mit. Er braucht weder eine Adresse im Panel noch einen selbst erzeugten Token. Unter Standorte → Privatzonen & KI kannst du Integrierter Gesichts-Worker pro Kamera als Gesichts-Engine wählen.

Wenn du das InsightFace-Modell für nichtkommerzielle Forschung verwenden möchtest, klicke auf ArcFace herunterladen (289 MB). Türwache legt den Ordner models in seinem Datenverzeichnis an, lädt das offizielle Archiv und prüft dessen Prüfsumme und die der enthaltenen Modelldatei. Sobald der Modellstatus die Installation meldet, aktiviere ArcFace für Kameras freigeben und prüfe die Verbindung. Bei SFace und ArcFace geprüft kannst du speichern, Referenzfotos einlernen und die Engine pro Kamera wählen. Alternativ erkennt der integrierte Worker eine manuell abgelegte w600k_r50.onnx unter ai/models im Projektordner. Modell und Lizenz

Worker separat betreiben

Für einen manuell gestarteten Worker wähle im Panel Separat im Heimnetz. Auch eine externe Worker-Instanz auf demselben PC ist möglich.

1. Token hinterlegen und Worker starten

Öffne ein zweites PowerShell-Fenster und wechsle in den Türwache-Projektordner. Die Datei .env gehört direkt in diesen Ordner neben package.json. Der Starter scripts/start-face-worker.mjs ist bereits vorhanden.


Set-Location 'C:\Pfad\zu\Tuerwache'
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
if (-not (Test-Path -LiteralPath '.env')) { New-Item -ItemType File -Path '.env' | Out-Null }
notepad .env

Füge in .env die Zeile FACE_WORKER_TOKEN=DEIN_ERZEUGTER_TOKEN hinzu und ersetze den Platzhalter durch den ausgegebenen Wert. Gibt es den Eintrag schon, verwende den vorhandenen Wert. Wenn du den Windows-Installer mit -WithAI verwendet hast, ergänze bei Bedarf AI_PYTHON=.venv/Scripts/python.exe, damit auch der Worker die virtuelle Umgebung nutzt.


node --env-file=.env scripts/start-face-worker.mjs

Sobald Gesichts-Worker läuft auf HTTP an Port 3211. erscheint, lass das Fenster offen. Türwache läuft parallel auf Port 3210.

2. Worker in Türwache verbinden

  • Öffne als Administrator KI-Anbieter → Gesichts-Worker. Gib bei Worker-Adresse http://127.0.0.1:3211 ein.
  • Füge bei Worker-Token den Wert aus .env ein. Trage nur den Wert hinter dem Gleichheitszeichen ein.
  • Lass ArcFace für Kameras freigeben für den ersten SFace-Test aus. Klicke auf Worker-Verbindung prüfen. Wenn SFace erfolgreich geprüft wurde, schalte Gesichts-Worker freigeben ein und speichere.
  • Aktiviere pro gewünschter Kamera die Gesichtserkennung und wähle unter Standorte → Privatzonen & KI → Gesichts-Engine den Gesichts-Worker im Heimnetz. Bei aktiven Privatzonen bleibt die Gesichtsauswertung auf Türwache.

Für ArcFace ergänze in .env FACE_WORKER_ARCFACE_MODEL=C:/Pfad/zu/w600k_r50.onnx mit dem geprüften Modell, starte den Worker erneut und schalte im Panel ArcFace für Kameras freigeben ein. Prüfe und speichere die Verbindung. Lerne unter Gesichter mindestens ein Referenzfoto pro Person ein und wähle an der Kamera ArcFace im Heimnetz. Hinweise zu Modell, Lizenz und Betrieb auf einem zweiten Gerät stehen in der Heimnetz-Anleitung.

Ollama optional

scripts/Start-Ollama.ps1 -Install installiert den optionalen lokalen Modellserver. Dies ist unabhängig von der lokalen OpenCV-Erkennung. Ein bildfähiges Modell installieren, unter KI-Anbieter konfigurieren und gezielt einer Kamera zuordnen. Große VLMs können ohne GPU langsam sein.

Autostart

Für einen ersten privaten Betrieb kann die Windows-Aufgabenplanung powershell.exe -NoProfile -File C:\Pfad\Tuerwache\scripts\Start-Tuerwache.ps1 bei der Benutzeranmeldung starten. Arbeitsverzeichnis auf den Projektordner setzen, keine parallelen Instanzen erlauben und unter einem normalen Benutzer ausführen. Dieser Autostart wird nicht ungefragt eingerichtet. Für einen dauerhaft unbeaufsichtigten Server ist der dokumentierte Linux-systemd-Weg vorzuziehen.

Linux und Server

Native Installation

Zielplattform: Debian/Ubuntu oder Raspberry Pi OS mit 64 Bit. Voraussetzungen: Bash, Node.js 24 LTS mit npm; für lokale KI Python 3.10–3.13, python3-venv, libglib2.0-0 und libgl1. Node über die offizielle Downloadseite installieren; ein veraltetes Distributionspaket reicht möglicherweise nicht. Python-Abhängigkeiten werden in einer eigenen virtuellen Umgebung installiert, nicht systemweit.


sudo apt-get update
sudo apt-get install -y git ca-certificates python3 python3-venv libglib2.0-0 libgl1
# Repository klonen, dann in seinen Ordner wechseln.
bash scripts/install-linux.sh --with-ai --check-only
bash scripts/install-linux.sh --with-ai
bash scripts/start-linux.sh

Ohne lokale Bildanalyse --with-ai weglassen. Der Installer benötigt beim eigentlichen Installieren Internet. Er nutzt npm ci, Python-Binärpakete und prüft die Modelldateien gegen das mitgelieferte SHA256-Manifest. Scheitert ein Binärpaket, nicht auf unkontrollierte Builds ausweichen: Python-/CPU-Version prüfen.

Als Dienst mit systemd

Für dieses einfache Dienstskript ist /opt/tuerwache verbindlich. Ein eigener Benutzer besitzt Quellcode und Daten. Beispiel nach Bereitstellung des Quellcodes:


sudo useradd --system --create-home --home-dir /var/lib/tuerwache --shell /usr/sbin/nologin tuerwache
sudo install -d -o tuerwache -g tuerwache /opt/tuerwache
# Bereinigten Quellcode als Benutzer tuerwache nach /opt/tuerwache übertragen.
cd /opt/tuerwache
sudo -u tuerwache bash scripts/install-linux.sh --with-ai
sudo -u tuerwache mkdir -p data
# Zuerst manuell starten, testen und wieder sauber stoppen.
sudo -u tuerwache bash scripts/start-linux.sh
sudo bash scripts/install-service.sh --user tuerwache
sudo systemctl status tuerwache
sudo journalctl -u tuerwache -f

Keine bereits verwendeten Konten-/Datenordner überschreiben. Das Dienstskript überschreibt keine vorhandene Unit. Stoppen: sudo systemctl stop tuerwache. Es wartet auf laufende Arbeit bis zu 260 Sekunden. Die Dienst-Härtung erlaubt Schreibzugriff nur auf data und temporäre Dateien. Für einen anderen Clip-Ordner braucht es zusätzlich einen gezielten ReadWritePaths-Eintrag und passende Dateirechte. Für Ollama einen eigenen Dienst verwenden; dieser Installer startet Ollama nicht.

Ersteinrichtung aus der Ferne

Standardmäßig lauscht der Server nur auf 127.0.0.1. Für die erste Anmeldung einen SSH-Tunnel öffnen:


ssh -L 3210:127.0.0.1:3210 user@server

Dann im eigenen Browser localhost:3210 öffnen. Später HTTPS, erlaubten Host und Zwei-Faktor-Anmeldung einrichten und erst danach unter Server & Zugriff freigeben. Details zu Betrieb und Sicherheit.

Docker

deploy/compose.yaml ist eine Linux-Vorlage mit Host-Netzwerk und optionalem Caddy-Profil. deploy/.env.example nach deploy/.env kopieren und eigene Domain sowie zufälligen 64-stelligen Hex-Schlüssel setzen. Den Schlüssel getrennt vom Datenbackup sichern. App zunächst mit docker compose -f deploy/compose.yaml up -d --build app starten; der HTTPS-Proxy wird erst mit Profil external bewusst gestartet. Einzelheiten in deploy/README.md im Repository. Diese Vorlage gilt nicht unverändert für Docker Desktop und mehrere Mandanten.

Raspberry Pi

Unter emuliertem Linux/ARM64 wurden der Serverstart, der FFmpeg-Start und das Einlernen sowie Wiedererkennen eines Testgesichts geprüft. Auf einem echten Pi stehen der Test mit Ring-Kameras und die Messung von Kameraanzahl, KI-Laufzeit und Temperatur noch aus.

Als Ausgangspunkt für einen Versuch: Pi 5 mit 8 GB RAM, 64-Bit-OS, aktiver Kühlung und SSD. Dies ist eine Einschätzung, keine gemessene Mindestanforderung. Offizielle Pi-5-Daten bestätigen die 64-Bit-Plattform.

Sinnvolle Aufteilung

  • Pi: Ereignisse, kurze Clips, Website und Benachrichtigungen.
  • OpenCV-Personen-/Gesichtserkennung: erst eine Kamera testen; Laufzeit, Temperatur und Warteschlange beobachten.
  • VLM-Beschreibungen: vorzugsweise anderer Rechner im privaten Netz mit Ollama/LM Studio/llama.cpp oder bewusst gewählter Cloud-Anbieter.

Ein großes VLM direkt auf dem Pi ist keine Voraussetzung. Daueraufnahme mit Akku-Ring-Geräten ist nicht vorgesehen. Unter Betrieb lässt sich das Limit für gleichzeitig genutzte Kamerastreams auf 1 bis 8 einstellen, mit 4 als Standard. Auf dem Pi zuerst mit einem Stream testen und erst nach Messung erhöhen.

Installation und Test

Linux-Anleitung verwenden. Bei diesem Ziel muss uname -m aarch64 zeigen. Ein 32-Bit-System ist nicht unterstützt. FFmpeg und die fixierten Python-Binärpakete müssen verfügbar sein; ansonsten abbrechen und Plattform prüfen.

Eine Kamera verbinden, Bewegung und Klingeln einzeln testen, Clip mit Ton abspielen und nach Neustart erneut prüfen. Erst dann lokale KI einschalten. Für den Umzug vom Windows-Server eine verschlüsselte Sicherung verwenden. Die Wiederherstellung schreibt absolute Clip-Pfade für den neuen Datenordner um.

Gesichts-Worker im Heimnetz

Wenn Türwache und der Worker auf demselben Gerät laufen, kannst du unter KI-Anbieter → Gesichts-Worker den integrierten Worker wählen und das ArcFace-Modell direkt im Panel herunterladen. Die Anleitung für den integrierten Worker zeigt die Einstellungen.

Auf dem zweiten Rechner Türwache samt OpenCV-Modellen installieren. Einen zufälligen Token erzeugen (node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))") und auf dem Worker in .env als FACE_WORKER_TOKEN hinterlegen. Dort auch die folgenden Werte setzen:


FACE_WORKER_HOST=192.168.1.10
FACE_WORKER_PORT=3211
FACE_WORKER_CERT=/path/to/cert.pem
FACE_WORKER_KEY=/path/to/key.pem
# AI_PYTHON=/opt/tuerwache/.venv/bin/python

Den Worker mit node --env-file=.env scripts/start-face-worker.mjs starten. Auf dem Pi unter KI-Anbieter → Gesichts-Worker die Worker-Adresse und denselben Token eintragen. Worker-Verbindung prüfen verwendet ein synthetisches Testbild. Die Verbindung freigeben und speichern. Läuft der Worker auf dem Pi selbst, verwende http://127.0.0.1:3211. Auf einem anderen Gerät muss die HTTPS-Adresse zum Zertifikat passen und in der Python-Umgebung des Pi vertrauenswürdig sein. In Standorte → Privatzonen & KI die Engine für die gewünschten Kameras wählen.

Optional ArcFace auf dem Worker nutzen

1. Auf dem leistungsstärkeren Worker FACE_WORKER_ARCFACE_MODEL auf das geprüfte Modell w600k_r50.onnx aus dem InsightFace-Paket buffalo_l setzen und den Worker neu starten. Türwache liefert die Gewichte nicht mit. InsightFace gibt diese öffentlichen Gewichte für nichtkommerzielle Forschung frei. Ihre Lizenzbedingungen gelten auch bei separatem Download. 2. Auf dem Pi unter KI-Anbieter → Gesichts-Worker ArcFace für Kameras freigeben aktivieren, die Verbindung prüfen und speichern. Unter Gesichter mindestens ein Referenzfoto für jede bekannte Person einlernen. Falls du genau dieselbe Datei erneut auswählst, ergänzt Türwache die bestehende Vorlage um ArcFace. 3. Pro Kamera unter Standorte → Privatzonen & KI → Gesichts-Engine ArcFace im Heimnetz auswählen. Aufnahme, Gesichtssuche im Video und Namensabgleich laufen auf dem Pi. Nur ausgerichtete Gesichtsausschnitte gehen an den Worker, der die ArcFace-Merkmale berechnet.

ArcFace nutzt die eigene Mindestähnlichkeit 0,30 und die Mehrbildbestätigung. Bei fehlenden ArcFace-Vorlagen, einem nicht erreichbaren Worker oder aktiven Privatzonen nutzt Türwache lokales SFace. Details stehen unter Gesichtserkennung im Clip.

Übertragen werden ausgerichtete Gesichtsausschnitte an den eigenen Worker. Die gespeicherten Vorlagen, Namen und der Abgleich bleiben auf Türwache. Ist der Worker nicht erreichbar oder sind für die Kamera Privatzonen gesetzt, berechnet Türwache die Merkmale lokal. Auf Loopback ist für einen Test auch HTTP möglich.

ONVIF und RTSP

  • Raspberry Pi OS 64 Bit und Node.js 24 verwenden. In Docker wird für die ONVIF-Suche unter Linux das Host-Netzwerk genutzt. Mit der manuellen Adresse funktioniert RTSP auch ohne Multicast.
  • Im Kameramenü H.264 und nach Möglichkeit einen Schlüsselbildabstand von rund zwei Sekunden wählen. Damit speichert Türwache den Videostream ohne erneute Kodierung. H.265-Umwandlung und Bewegungserkennung je Kamera bei Bedarf aktivieren und die CPU-Auslastung prüfen.
  • Den Pufferordner und die Clips auf einer SSD ablegen. Das Netzwerkkamera-Limit steht unter Betrieb. Netzwerkkameras einrichten

Kameras, KI und Fehler finden

Aufnahmen

Türwache- und Ring-Konto sind getrennt. Unter Kameras pro Gerät Überwachung, Bewegung/Klingeln, Dauer, Mindestabstand, Erkennung, Beschreibungsmodell und Discord wählen. Ein gespeichertes Modell allein aktiviert keine Kameraanalyse.

Eine manuelle Aufnahme unter Übersicht prüfen. Unter Clips stehen gespeicherte Videos; der Zeitstrahl verbindet Ereignisse, Aufnahmezustand und Beschreibungen. Bewegungsmeldung bedeutet nicht automatisch gespeicherte Aufnahme.

Warum fehlt ein Clip oder ein Teil des Besuchs?

Neue Clips werden vor Veröffentlichung vollständig auf Decoderfehler und größere Zeitlücken geprüft. Eine Warnung im Cliparchiv weist auf beeinträchtigte Aufnahmen hin. Größere Empfangspuffer, längere Paket-Nachforderungen und eine normale MP4-Datei mit vorangestelltem Index verbessern die Übertragung und Wiedergabe; sie erzeugen keine verlorenen Kamerabilder und erhöhen nicht die tatsächliche Kamerabildrate.

Aufnahmen und Web-Livebild kopieren jetzt das empfangene H.264-Videobild ohne lokale Verkleinerung oder FPS-Filter. Im Livebild wird die gemessene Auflösung und ungefähre Bildrate angezeigt. Die vom Ring-Dienst tatsächlich gelieferte Qualität kann je Sitzung abweichen. Kameraton wird für kompatible Wiedergabe weiterhin nach AAC umgewandelt. Die frühere feste Live-Begrenzung auf 720 Pixel und 15 FPS ist entfernt. HLS hat weiterhin einen Wiedergabepuffer und damit mehr Verzögerung als eine direkte WebRTC-Verbindung.

Die FPS-Anzeige wird aus dekodierten Bildern des ersten Live-Segments berechnet. Eine im Transport-Header angekündigte Bildrate kann davon abweichen und ist kein Nachweis tatsächlich gelieferter Bilder.

  • Aufnahme ausgeschaltet oder Server beim Ereignis nicht aktiv.
  • Mindestabstand seit letztem Aufnahmestart noch nicht erreicht.
  • Eine andere Aufnahme läuft: aktuell höchstens eine gleichzeitig.
  • Akku-Kamera wacht verspätet auf, Live-Verbindung scheitert oder Speicher fehlt.
  • Der spätere Teil des Besuchs liegt nach Clipende, ohne weiteres verwertbares Ereignis.

Ereignisdetails und Aufnahme-/KI-Zustand lesen. Dauer/Abstand pro Kamera ändern; dies kann Akku kosten. Nicht aufgenommene Bilder sind nicht rückwirkend verfügbar. Alte tonlose Clips bekommen keinen Ton. Neue Clips und Livebild verwenden Kameraton, sofern Ring ihn liefert; Playerlautstärke prüfen.

Gesichter und VLM

OpenCV erkennt Personen und Gesichter lokal. Pro Person bis zu zwölf Fotos mit verschiedenen Blickwinkeln/Lichtbedingungen einlernen, jeweils genau ein klares Gesicht und Einverständnis der Person. Unter Gesichter Vorlagen ergänzen/entfernen oder unbekannte Vorschläge selbst zuordnen.

Wenn Türwache ein Gesicht findet, aber den Namen selten bestätigt, ergänze eine scharfe Vorlage aus demselben Kamerawinkel. Wähle dafür einen sichtbaren Ausschnitt unter Unbekannte Gesichter zuordnen und verwende den vorhandenen Namen. Starte danach im Clip die KI-Auswertung erneut. Türwache nutzt beim Ausschneiden die Originalauflösung und passt bei dunklen Ausschnitten lokal die Helligkeit an. Mehr Licht und eine kurze Sicht von vorn helfen besonders bei kleinen oder unscharfen Gesichtern.

Automatische Namen erfordern konsistente Bestätigung in mindestens drei verschiedenen Frames mit zeitlichem Abstand. Unsichere oder widersprüchliche Treffer bleiben unbestätigt. Ähnlichkeit ist keine Wahrscheinlichkeit. Ein dauerhafter Python-Worker hält Modelle geladen und verarbeitet Aufträge nacheinander.

Das VLM bekommt keine lokale Namensliste oder Gesichtsvektoren. Verifizierte Namen werden separat aus der lokalen Mehrbilderkennung ergänzt; dies beweist keine vom Modell beschriebene Handlung. KI-Texte können falsch sein. Referenzänderungen machen ältere automatische Identitätsbelege ungültig. Bereits versandte Discord-Nachrichten werden dadurch nicht zurückgerufen.

Modelle auswählen

Unter KI-Anbieter Modelle hinzufügen, bearbeiten, prüfen und entfernen. Lokale Server: Ollama, LM Studio, llama.cpp, LocalAI und vLLM. Cloud: gängige Anbieter und OpenAI-kompatible Schnittstellen. Ein bildfähiges Modell ist nötig.

Mehrere Modelle können gespeichert sein; jede Kamera verwendet genau ihr gewähltes Beschreibungsmodell, ohne automatischen Cloud-Fallback. Lokale Gesichtserkennung kann parallel laufen: Sie bestimmt Identitäten, das VLM beschreibt Bilder.

Cloud-Aufrufe übertragen ausgewählte Frames und die Ortsbeschreibung. Alle Cloud-Anbieter teilen ein konfigurierbares tägliches Anfragelimit in UTC, inklusive Fehlern. Dies ist kein Geldlimit. Anbieterpreise/Datenbedingungen selbst prüfen.

Discord und Speicher

Eigenen Webhook hinterlegen und Kamera-Schalter für Klingeln, Clip und Personen-/Zusammenfassungsbild aktivieren. Ein Personenbild braucht erfolgreiche Personenerkennung, ein Zusammenfassungsbild eine erfolgreiche Beschreibung. Dateigrößenlimits und Webhook-Fehler können Anhänge verhindern. Alte Ereignisse werden nicht automatisch erneut gesendet. Manuelle Analysen lösen keine automatischen Meldungen aus.

Clips bleiben lokal oder in einem anderen beschreibbaren Ordner; optional private R2-/S3-Kopie aktivieren. Cloudvideos ersetzen kein vollständiges App-Backup. Zugangsschlüssel nur auf dem eigenen Server eingeben.

Standorte und Benutzer

Unter Ring-Konten kannst du weitere Konten mit eigener Anmeldung und eigener 2FA verbinden. Geteilte Ring-Kameras erscheinen einmal in Türwache. Unter Standorte kannst du die übernommenen Ring-Standorte umbenennen, eigene Standorte anlegen und Kameras zuordnen. Hier stehen Kamerastatus und letztes Klingel- oder Bewegungsereignis. Alte Aufnahmen bleiben beim Trennen eines Kontos verfügbar.

Unter Benutzer öffnest du Rechte bearbeiten bei einer Rolle oder Konto & Rechte bei einem Benutzer. Wähle unter Kamerazugriff die Standorte und Kameras aus und öffne Rechte neben dem jeweiligen Namen. Clips ansehen, exportieren, schützen und löschen lassen sich einzeln einstellen. Aktionen an einem Clip setzen das Recht Clips ansehen voraus. Benutzerspezifische Regeln haben Vorrang vor der Rolle. Bei mehreren passenden Regeln derselben Ebene gilt die Sperre. Die Administratorrolle hat Vollzugriff.

Unter Handy-App → Push-Ruhezeiten oder Mein Handy in der App stellst du ein Zeitfenster und die Zeitzone ein. Die Einstellung gilt pro Benutzer für dessen Geräte. Klingeln kann als Ausnahme zugelassen werden.

Privatzonen und Gesichts-Engine

Im Standort bei der Kamera Privatzonen & KI öffnen und Rechtecke zeichnen oder ihre Position in Prozent eingeben. Der explizite Clip-Download und Discord-Anhänge decken die Bereiche schwarz ab. Einzelbilder für Szenenbeschreibungen erhalten dieselben Masken. Das Original mit Ton steht weiterhin den Benutzern offen, die Clip-Wiedergabe für diese Kamera dürfen. Geschützte Backups und private R2-/S3-Speicherkopien archivieren das Original. Bereits versandte Anhänge behalten ihren damaligen Stand.

Die Gesichtsprüfung liest am Clipanfang und in der Nähe von Personensichtungen zusätzliche Bilder. Ein Name braucht weiterhin drei verschiedene, übereinstimmende Bilder. Bei Bedarf kann ein Gesichts-Worker im Heimnetz die Bildmerkmale berechnen. Kameras mit Privatzonen verwenden für Gesichter die lokale Engine.

Ring und Netzwerkkameras verbinden

Ring, ONVIF und RTSP können in derselben Installation laufen. Öffne als Administrator Kameraverbindungen → Kamera hinzufügen und wähle im Dialog den Verbindungstyp. Mit Ring legst du einen Kontonamen fest und meldest dich anschließend bei Ring an. Türwache übernimmt die Kameras dieses Kontos.

ONVIF im Netzwerk suchen

  • Aktiviere ONVIF im Kameramenü. Manche Kameras verlangen ein eigenes ONVIF-Konto. Prüfe, dass Kamera und Türwache im erreichbaren Heimnetz liegen.
  • Wähle im Dialog ONVIF.
  • Klicke auf Im Netzwerk suchen, wähle die Kamera und gib ihre Zugangsdaten ein. Falls die Suche kein Ergebnis zeigt, trage die ONVIF-Dienstadresse direkt ein. Ein Beispiel ist http://192.168.1.20/onvif/device_service.
  • Lade die Videoprofile und wähle möglichst H.264. Bei mehreren Kanälen eines Rekorders kannst du das gewünschte Profil wählen und weitere Kanäle separat hinzufügen.
  • Stelle die Voraufnahme ein und klicke auf Kamera verbinden. Sobald fertig geschriebene Segmente vorliegen, zeigt Türwache die Kamera als online an.

Die Suche verwendet IPv4-Multicast im lokalen Netz. Getrennte VLANs, Gastnetze, lokal gefilterter Multicast und Docker-Netzwerkbrücken können die Suche verhindern. Mit der manuellen ONVIF- oder RTSP-Adresse funktioniert die Verbindung auch ohne Multicast, sofern die Kamera erreichbar ist. Türwache fragt ONVIF-Medienprofile ab. Bewegungsmeldungen aus dem Kameraprotokoll, Gegensprechen und PTZ-Steuerung sind in dieser Integration nicht eingerichtet. ONVIF Profile T

RTSP-Adresse manuell eintragen

  • Wähle RTSP und trage die Stream-Adresse ein, zum Beispiel rtsp://192.168.1.20:554/stream1. Pfad und Port stehen in der Anleitung der Kamera oder des Rekorders.
  • Gib Benutzername und Passwort in den separaten Feldern ein. Die gespeicherte Verbindung ist verschlüsselt, und die Oberfläche liefert das Kennwort später nicht zurück.
  • Bei H.264 bleibt das Video beim Schreiben des Puffers unverändert kodiert. Für H.265 kannst du die H.264-Umwandlung unter Weitere Stream-Einstellungen einschalten, falls dein Browser den Stream sonst nicht abspielt. Auf dem Raspberry Pi ist ein H.264-Kameraprofil vorzuziehen.

Voraufnahme, Bewegung und Speicher

Bei aktiver Überwachung liest Türwache den Netzwerkstream fortlaufend und hält die jüngsten Videosegmente im lokalen Ordner data/network-buffer. Der Puffer wird laufend überschrieben. Er steht bei manuellen Aufnahmen und bei aktivierter softwarebasierter Bewegungserkennung zur Verfügung. Du kannst 0, 5, 10 oder 15 Sekunden wählen.

Die tatsächliche Voraufnahme hängt vom bereits gefüllten Puffer und den Schlüsselbildern der Kamera ab. Mit H.264 und einem Schlüsselbildintervall von rund zwei Sekunden sind die Aufnahmegrenzen genauer. Bei einer Unterbrechung speichert Türwache die noch lesbaren Segmente und markiert einen verkürzten Clip. Bei Ring ohne dauerhaften Stream bleibt die Aufnahme nach dem bisherigen Ring-Ablauf.

Bewegungserkennung vergleicht kleine Graustufenbilder und kann auf Lichtwechsel oder Wetter reagieren. Unter Weitere Stream-Einstellungen lässt sich eine zweite RTSP-Adresse für die Bewegungserkennung hinterlegen. Türwache speichert den Hauptstream weiter in voller Auflösung und verbindet den Zweitstream bei Unterbrechungen separat neu.

Personen- und Gesichtserkennung sind separate Auswertungen am gespeicherten Clip. Auf dem Raspberry Pi helfen ein kleiner Zweitstream und ein niedriger Grenzwert aktiver Streams unter Betrieb. Speicher- und SSD-Auslastung vor mehreren Dauerstreams prüfen. Raspberry-Pi-Anleitung

Sicherheit, Backup und Updates

Externer Zugriff

Standard: Loopback und Freigabe aus. Für Heimserver oder Cloud eigene HTTPS-Adresse, erlaubte Hosts, exakt vertraute Proxy-IP und MFA für alle Benutzer einrichten. Cloud benötigt einen AUTH_ENCRYPTION_KEY außerhalb des Datenvolumens. Erst danach unter Server & Zugriff Betriebsort wählen und freigeben. Die vollständige Proxy-Anleitung steht in deploy/README.md.

Keine öffentliche Weiterleitung direkt auf den Node-Port und keine beliebigen Forwarded-Header vertrauen. VPN ist eine weitere Option, benötigt ebenfalls richtige Konfiguration. Vor Kundenbetrieb die öffentliche Anmeldung unabhängig prüfen lassen. Es gibt keine 100-%-Sicherheitszusage.

Aufbewahrung und Schutz

Unter Betrieb → Aufbewahrung gibt es getrennte, standardmäßig ausgeschaltete Regeln für lokale Clips (Alter und GiB-Limit) und R2/S3-Kopien (Alter und optionales GiB-Limit; 0 = unbegrenzt). Vorher gespeicherte Regeln als Vorschau prüfen. Bei Aktivierung läuft die Prüfung alle fünf Minuten. Ein unter Clips geschütztes Video wird von beiden Regeln ausgenommen; laufende Verarbeitung wird übersprungen. Eine volle Platte lässt sich bei vielen geschützten Clips dadurch nicht automatisch bereinigen.

Bleibt nur die Cloud-Kopie, erfolgt die Wiedergabe nach Anmeldung über den Server; der Bucket bleibt privat. Zum Lesen/Löschen müssen ursprünglicher Endpunkt, Region, Bucket und passende Zugangsdaten verfügbar sein. Eine abgelaufene Aufnahme bleibt als Ereignis erhalten. Die Cloud-Quote zählt bekannte Clipgrößen dieser Installation; fremde Bucket-Dateien werden nicht verwaltet. Aufbewahrung ersetzt keine Datensicherung.

Verschlüsselte Sicherungen

Betrieb → Sicherungen erstellt ein passphrasengeschütztes .twbackup mit scrypt und AES-256-GCM. Mindestens 16 Zeichen verwenden und die Passphrase getrennt aufbewahren. Gesichert werden Benutzer/MFA, effektiver Verschlüsselungsschlüssel, Ring-Sitzung, Einstellungen, Ereignisse, Gesichter, Bewertungen und optional Videos. Browser-/Handy-Sitzungen werden nicht übernommen. Modellgewichte, Python, Software und .env gehören nicht ins Archiv. .env, insbesondere externe Zugangskonfiguration und EXPO_ACCESS_TOKEN, zusätzlich getrennt schützen.

Manuelle Sicherungen bleiben erhalten. Ein optionaler Zeitplan speichert seine Passphrase verschlüsselt auf dem Server und begrenzt nur seine eigenen geplanten Sicherungen. Sicherungen vom selben Laufwerk auf ein zweites Gerät herunterladen. Das Archiv enthält sensible Daten und ist nicht zur Veröffentlichung bestimmt.

Geprüfte Wiederherstellung / Windows → Linux oder Pi

1. Auf dem Zielsystem dieselbe oder eine kompatible Türwache-Version und die benötigten Python-/KI-Komponenten installieren. Alten Server stoppen; nie beide mit derselben Ring-Sitzung oder Datenablage betreiben. 2. Archiv nach backups/snapshots/UUID.twbackup kopieren (oder BACKUP_DIRECTORY verwenden), im Web unter Sicherungen prüfen und die erhaltene Prüfungskennung notieren. Eine Prüfung verändert die laufenden Daten nicht. 3. Zielserver sauber stoppen. Im Projektordner erst ohne --apply prüfen; dann bewusst anwenden:


node scripts/restore.mjs --verification PRUEFUNGS-UUID
node scripts/restore.mjs --verification PRUEFUNGS-UUID --apply

Die Wiederherstellung prüft alle Dateien/Hashes und erstellt eine geprüfte Arbeitskopie neben dem Ziel-Datenordner. Erst dann werden bisherige Daten nach .tuerwache-previous-UUID verschoben und die vorbereiteten Daten aktiviert. Bei Aktivierungsfehler wird zurückgerollt. Vorherige Daten bleiben erhalten; später nur nach erfolgreicher Prüfung manuell entfernen. Genügend Platz für Archiv, entschlüsselte Prüfung und Arbeitskopie einplanen.

Absolute Clip-Pfade werden für DATA_DIRECTORY neu geschrieben. Ein gesetzter AUTH_ENCRYPTION_KEY muss zum importierten Schlüssel passen. Beim ersten Start müssen Benutzer/Handys neu angemeldet werden. Fernzugriff bleibt aus; Aufbewahrung, Backup-Zeitplan und Discord-Betriebswarnungen werden ausgeschaltet und müssen geprüft neu aktiviert werden.

Bei Docker liegt DATA_DIRECTORY bei Neuinstallationen auf /app/data/state, Backups auf einem eigenen Volume. Ein Volume-Wurzelordner lässt sich nicht austauschen: bestehende Container mit älterem /app/data-Layout vor einer Umstellung sichern und gezielt in einen Datenunterordner migrieren. Restore-CLI im gestoppten Dienst mit denselben Mounts und Umgebungswerten ausführen. Ein Pi kann die Daten übernehmen; lokale VLM-Leistung hängt stark von Modell/RAM ab. Große Beschreibungsmodelle besser auf einem separaten Rechner betreiben.

Betrieb und Wiederholungen

Unter Betrieb stehen Ring-/Ereignisverbindung, Offline-Kameras, Plattenplatz, lange Jobs, Zustellfehler und die Wiederholungswarteschlange. Optional sind neutrale Discord-Betriebswarnungen höchstens alle 30 Minuten möglich; standardmäßig aus. Die Ereignis-Stille ist standardmäßig kein Alarm: eine ruhige Szene kann normal sein.

Neue Fehler bei lokaler KI, Beschreibungen und Uploads können begrenzt und dauerhaft gespeichert erneut versucht werden. Pausierte Kameras und inzwischen entfernte lokale Videos werden übersprungen. Ein unklarer Discord-/Push-Versand wird nicht automatisch erneut gesendet. Expo-Zustellbelege zeigen die Übergabe an Apple/Google, nicht die Anzeige beim Nutzer. Abgelehnte Geräte-Tokens werden entfernt. Ein Push-Test lässt sich nur für die eigene Handy-Sitzung auslösen.

KI-Qualität

Am Clip Richtig/Falsch/Unsicher und optional eine Korrektur speichern. Die Bewertung gehört zur jeweiligen Beschreibungsversion und verändert sie nicht. Unter KI → KI-Qualität ausgewählte Modelle anhand derselben bis zu sechs Einzelbilder vergleichen. Cloud-Aufrufe benötigen ausdrückliche Bildfreigabe, zählen zum Tageslimit und können Gebühren verursachen. Vergleiche senden keine Discord-/Push-Nachrichten und überschreiben keine ursprüngliche Zusammenfassung. Auch Vergleichsergebnisse sind bewertbar. Es findet kein automatisches Training statt.

Update

Änderungen prüfen, Backup, stoppen, Quellcode aktualisieren und Installer mit passender AI-Option erneut ausführen. Starten und neues Ereignis mit Bild/Ton prüfen. Bei Fehlschlag alten Code und zugehöriges Datenbackup gemeinsam wiederherstellen. Nie zwei Prozesse gegen dieselbe JSON-Datenablage starten.

Install and start

Clone the private repository or use the cleaned source export. Open PowerShell in a directory owned by your normal user. Do not run the server as Administrator.


powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Install-Windows.ps1 -WithAI -CheckOnly
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Install-Windows.ps1 -WithAI
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-Tuerwache.ps1

Omit -WithAI if local person/face recognition is not needed. Installation uses the npm lockfile, installs FFmpeg and optional Python packages, and verifies three OpenCV model files with SHA256. It does not start the server. CheckOnly checks prerequisites without downloads or changes.

Open Türwache, create the first Türwache administrator, then connect Ring and enter its verification code. Enter passwords only in your own local app.

Configuration and startup

Optionally copy .env.example to .env. The new launch scripts read this file; plain npm start does not. The local .venv/Scripts/python.exe is selected automatically unless AI_PYTHON is configured. Stop with Ctrl+C and let ongoing work drain. Back up and stop before upgrading. Never run two instances against one data directory.

Start-Tuerwache.cmd uses the same launcher. Optional local VLM installation is separate: scripts/Start-Ollama.ps1 -Install. Configure a vision-capable model and select it per camera. Large models can be slow without a GPU.

Run the worker separately

For a manually started worker, select Separate worker on the local network. You can also run this separate instance on the same PC.

1. Set the token and start the worker

Open a second PowerShell window in the Türwache project folder. Put .env next to package.json in that folder. The scripts/start-face-worker.mjs launcher is already included.


Set-Location 'C:\Path\to\Tuerwache'
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
if (-not (Test-Path -LiteralPath '.env')) { New-Item -ItemType File -Path '.env' | Out-Null }

Add FACE_WORKER_TOKEN=YOUR_GENERATED_TOKEN to .env, replacing the placeholder with the generated value. If the entry already exists, reuse its value. If you used the Windows installer with -WithAI, add AI_PYTHON=.venv/Scripts/python.exe if needed so the worker uses that Python environment.

Keep the window open once you see Gesichts-Worker läuft auf HTTP an Port 3211. (the worker is running on HTTP port 3211). The Türwache app continues to run on port 3210.

Linux and servers

Native installation

Target: Debian/Ubuntu or 64-bit Raspberry Pi OS. Requirements: Bash, Node.js 24 LTS with npm; for local AI, Python 3.10–3.13, python3-venv, libglib2.0-0 and libgl1. Install Node from its official distribution. Python packages go into a virtual environment, never the system Python.


sudo apt-get update
sudo apt-get install -y git ca-certificates python3 python3-venv libglib2.0-0 libgl1
# Clone the repository and enter its directory.
bash scripts/install-linux.sh --with-ai --check-only
bash scripts/install-linux.sh --with-ai
bash scripts/start-linux.sh

Omit --with-ai without local image analysis. Installation requires internet, uses npm ci and Python binary wheels, and verifies model SHA256 hashes. If no wheel is available, review the CPU/Python combination instead of starting uncontrolled source builds.

systemd service

The simple service helper requires /opt/tuerwache. Create a dedicated user and copy clean source under that user's ownership:


sudo useradd --system --create-home --home-dir /var/lib/tuerwache --shell /usr/sbin/nologin tuerwache
sudo install -d -o tuerwache -g tuerwache /opt/tuerwache
# Transfer clean source into /opt/tuerwache as user tuerwache.
cd /opt/tuerwache
sudo -u tuerwache bash scripts/install-linux.sh --with-ai
sudo -u tuerwache mkdir -p data
# Test a manual start and stop cleanly before installing the service.
sudo -u tuerwache bash scripts/start-linux.sh
sudo bash scripts/install-service.sh --user tuerwache
sudo systemctl status tuerwache
sudo journalctl -u tuerwache -f

Never overwrite an existing installation's accounts/data. Existing service units are preserved. Stop using sudo systemctl stop tuerwache; shutdown allows up to 260 seconds for work to drain. Hardening permits writes only to data and temporary storage. Custom clip directories require an explicit ReadWritePaths entry and file permissions. Run Ollama as its own service.

Remote first setup

The app listens on loopback. Open an SSH tunnel, then browse localhost:3210:


ssh -L 3210:127.0.0.1:3210 user@server

Configure HTTPS, allowed hosts and MFA before enabling Server & access. See operations.

Docker

deploy/compose.yaml is a Linux host-network template with an optional Caddy profile. Copy deploy/.env.example to deploy/.env, set a domain and a private random 64-character hex encryption key. Back up the key separately. Start the app first using docker compose -f deploy/compose.yaml up -d --build app. Public HTTPS requires explicitly starting the external profile after setup. See deploy/README.md. This template is not directly suitable for Docker Desktop or multiple tenants.

Raspberry Pi

Server and FFmpeg startup, face enrollment, and recognition with a test face were verified under Linux/ARM64 emulation. Testing with Ring cameras and measuring camera capacity, AI latency, and temperature still require physical Pi hardware.

A possible starting point is Pi 5 with 8 GB RAM, 64-bit OS, active cooling and SSD. This is an estimate, not a measured minimum. Official Pi 5 specifications confirm the 64-bit platform.

Suggested split

  • Pi: events, short clips, website and notifications.
  • OpenCV person/face recognition: test one camera first; monitor latency, temperature and queue growth.
  • VLM descriptions: preferably another private-network computer with Ollama/LM Studio/llama.cpp, or an explicitly selected cloud provider.

A large VLM on the Pi is optional. Continuous battery-camera recording is not supported. In Operations, the limit for simultaneous camera streams is configurable from 1 to 8, with a default of 4. Start with one stream on the Pi and measure performance before raising the limit.

Installation and acceptance

Follow Linux setup. For this target, uname -m should report aarch64. A 32-bit OS is unsupported. FFmpeg and pinned Python binary wheels must be available; stop and investigate otherwise.

Test one camera, separate motion and doorbell events, audio playback, and restart recovery before enabling local AI. Use an encrypted backup to migrate from Windows. The restore process rewrites absolute clip paths for the new data directory.

Optional ArcFace on the worker

1. On the more powerful worker, set FACE_WORKER_ARCFACE_MODEL to the verified w600k_r50.onnx model from InsightFace buffalo_l and restart the worker. Türwache does not distribute the weights. InsightFace publishes these weights for non-commercial research under its model terms. 2. Only aligned face crops go to the worker. The gallery, names and matching stay on Türwache. A worker failure or configured privacy zones trigger local processing. Loopback HTTP is available for local testing.

ONVIF and RTSP

  • Use 64-bit Raspberry Pi OS and Node.js 24. On Linux, the Docker deployment uses host networking for ONVIF discovery. A manually entered RTSP address works without multicast.
  • Choose H.264 in your camera settings with a keyframe interval around two seconds. Türwache then copies the video without another encode. Enable H.265 conversion and software motion detection per camera when needed and check CPU usage.
  • Store the rolling buffer and clips on an SSD. Under Operations, set the network stream limit. Network camera setup

Cameras, AI and troubleshooting

Recordings

Türwache and Ring accounts are separate. Configure monitoring, motion/doorbell recording, duration, cooldown, detection, description model and Discord per camera. Saving a model does not enable camera analysis by itself.

Test a manual recording on Overview. Clips contains saved video; Timeline combines events, recording state and descriptions. A motion alert does not necessarily mean video was saved.

Missing clips or missing parts of a visit

New clips receive a full-video check for decoder errors and larger timestamp gaps before publication. Impaired recordings show a warning in the archive. Larger receive buffers, longer packet retransmission windows and conventional fast-start MP4 improve delivery/playback; they cannot recreate missing camera images or increase the camera's actual frame rate.

Recordings and web live view now copy the received H.264 video without local resizing or FPS filters. Live view shows measured dimensions and approximate frame rate. Ring may deliver different quality between sessions. Audio is still converted to AAC for compatibility. The former fixed 720-pixel/15-FPS live limit is removed. HLS buffering still adds latency compared with a direct WebRTC connection.

Displayed FPS is calculated from decoded frames in the first live segment. Nominal transport-header rates may differ and do not prove that the corresponding number of images arrived.

  • Recording disabled or server offline at event time.
  • Cooldown since the previous recording start not reached.
  • Another recording running: only one is supported at a time.
  • Late battery-camera wake-up, live setup failure or unavailable storage.
  • The later part happened after clip end without another usable event.

Read event and analysis status. Adjust duration/cooldown per camera, considering battery use. Unrecorded past images cannot be recovered. Old silent clips cannot gain audio. New clips and live view use camera audio when Ring supplies it; check volume controls.

Faces and VLM

OpenCV detects people/faces locally. Enrol up to twelve photos per person with different angles/lighting, exactly one clear face each, and consent. Add/remove templates or assign unknown suggestions under Faces.

If Türwache finds a face but rarely confirms the name, add a sharp reference from the same camera angle. Under Assign unknown faces, choose a clear crop and use the existing name. Then run AI analysis again for that clip. Türwache crops from the original resolution and adjusts brightness locally for dark crops. Better lighting and a brief front-facing view help with small or blurred faces.

Automatic names need consistent support across at least three distinct frames with a time span. Uncertain/conflicting matches remain unconfirmed. Similarity is not probability. A persistent Python worker caches models and processes jobs serially.

The VLM receives neither the local name list nor face vectors. Verified names are appended separately from local recognition; they do not prove a generated action. Descriptions can be wrong. Reference changes invalidate older automatic identity evidence, but cannot recall existing Discord messages.

Model selection

Add/edit/check/remove models under AI providers. Local options include Ollama, LM Studio, llama.cpp, LocalAI and vLLM; cloud presets and OpenAI-compatible APIs are available. Models must support images.

Several models can be saved; each camera uses its selected description model without automatic cloud fallback. Local face recognition can run alongside it: one establishes identities, the other describes frames.

Cloud calls send sampled frames and location context. All cloud providers share a configurable UTC daily request limit, including failures. This is not a spending cap. Review provider pricing/data terms.

Discord and storage

Configure your webhook and per-camera doorbell/clip/person/summary switches. Images require successful corresponding analysis. Attachment limits/webhook errors can prevent delivery. Old events are not resent automatically. Manual analysis does not trigger automatic notifications.

Store clips locally or in another writable directory, optionally with private R2/S3 copies. Cloud videos are not complete app backups. Enter keys only on your own server.

Sites, users and push

Connect additional Ring accounts under Ring accounts. Each has its own credentials and MFA. Shared Ring devices appear once in Türwache. Sites lists camera status and the latest doorbell or motion event. Administrators can rename sites, create new ones and move cameras between them.

Under Users, open Edit permissions for a role or Account & permissions for a user. Choose which sites and cameras are in scope, then open Permissions next to a camera to set its individual actions. Clip actions require permission to view clips. User rules take precedence over role rules. Within the same level, a matching deny wins. Administrators have full access.

Push quiet hours can be set on the mobile page or in the native app. They apply to all devices for the user, with an optional doorbell exception.

Open Privacy zones & AI for a camera to draw masks. The masks apply to explicit clip exports, Discord media and frames for scene descriptions. Playback, encrypted backups and private R2/S3 copies retain the original. A private face worker can calculate face embeddings when the camera has no privacy zones.

Connect Ring and network cameras

Run Ring, ONVIF and RTSP cameras in the same installation. As an administrator, open Camera connections → Add camera and select the connection type in the dialog. Choose Ring, give the connection a name and sign in to Ring. Türwache imports the cameras on that account.

Discover a camera over ONVIF

  • Enable ONVIF in the camera settings. Some cameras need a dedicated ONVIF account. Make sure the server can reach the camera on the local network.
  • Choose ONVIF in the dialog.
  • Select Search the network, choose the camera and enter its credentials. If discovery shows nothing, type the service address manually. An example is http://192.168.1.20/onvif/device_service.
  • Load the video profiles and choose H.264 when available. When adding a recorder with multiple channels, select the desired profile and add other channels separately.
  • Choose the pre-recording time and select Connect camera. The status turns online after the first complete video segments arrive.

Discovery uses local IPv4 multicast. VLANs, guest networks, multicast filtering and Docker bridge networking can prevent discovery. Entering a reachable ONVIF or RTSP address bypasses the need for discovery. Türwache reads ONVIF media profiles. Camera-event subscriptions, talkback and PTZ controls are outside this integration. Enter an RTSP address

  • Choose RTSP and enter the stream address, such as rtsp://192.168.1.20:554/stream1. Check the camera or recorder manual for its path and port.
  • Enter the camera username and password in the dedicated fields. The saved connection is encrypted and the password is never returned to the browser.
  • H.264 video is copied into the buffer without another encode. Enable H.264 conversion under More stream settings for an H.265 stream if your browser needs it. On a Raspberry Pi, choose H.264 directly on the camera whenever possible.

Pre-recording, motion and storage

While monitoring is enabled, Türwache reads the network stream continuously and keeps recent video segments under data/network-buffer. The rolling buffer is replaced as new footage arrives. It is available for manual recordings and software motion triggers. Set the target to 0, 5, 10 or 15 seconds.

The actual pre-recorded time depends on the available footage and the camera's keyframes. H.264 with a keyframe interval around two seconds makes recording boundaries more predictable. If the stream is interrupted, Türwache retains readable segments and marks the shorter clip. Ring cameras without a continuous stream continue to record through the existing Ring connection.

Motion detection compares small grayscale frames and can react to lighting changes or weather. Under More stream settings, you can supply a separate RTSP address for motion detection. The primary stream keeps its full recording resolution, and the substream reconnects independently after interruptions.

Person and face detection run separately on saved clips. On a Raspberry Pi, use a small substream and a low limit for active streams under Operations. Check the storage load before adding multiple continuous streams. Raspberry Pi guide

Security, backups and upgrades

External access

Default: loopback, external access disabled. For home/cloud, configure HTTPS origin, allowed hosts, exact proxy IP and MFA for every user. Cloud needs a separate AUTH_ENCRYPTION_KEY outside the data volume. Then select deployment mode and enable access. Full proxy setup is in deploy/README.md.

Do not forward public traffic directly to Node or trust arbitrary forwarding headers. VPN access also requires correct configuration. Independently review public authentication before serving customers. Perfect security is not promised.

Retention and protection

Operations → Retention has independent local age/GiB and cloud age/GiB rules (cloud quota 0 = unlimited), disabled by default. Preview saved rules before enabling automatic checks every five minutes. Protected clips are excluded from both rules; active processing is skipped. Protected footage can prevent the configured quota from being met.

Cloud-only playback is authenticated and proxied through the server; buckets stay private. Reading/deleting requires the original endpoint, region, bucket and credentials. Expired recordings remain as events. Cloud quota uses tracked clip sizes; unrelated bucket objects are not managed. Retention is not a backup.

Encrypted backups

Operations → Backups creates a .twbackup protected with scrypt and AES-256-GCM. Use at least 16 characters and keep the passphrase separately. Archives include users/MFA, the effective encryption key, Ring session, settings, events, face templates, reviews and optional videos. Browser/phone sessions are excluded. Software, Python, model weights and .env are excluded; protect environment configuration and EXPO_ACCESS_TOKEN separately.

Optional scheduled backups store a sealed passphrase locally. Their retention count applies only to scheduled archives; manual backups are kept. Download a copy to a separate device. Archives contain sensitive data and must not be published.

Verified restore / migration to Linux or Pi

1. Install a compatible Türwache version and Python/AI dependencies on the destination. Stop the old server; never share one Ring session/data directory between active instances. 2. Copy the archive to backups/snapshots/UUID.twbackup (or BACKUP_DIRECTORY), verify it through the web backup page and note the verification ID. Verification does not change live data. 3. Stop the destination server. From its project directory, dry-run first, then explicitly apply:


node scripts/restore.mjs --verification VERIFICATION-UUID
node scripts/restore.mjs --verification VERIFICATION-UUID --apply

Restore checks all files/hashes, creates and checks a working copy beside the destination directory, moves previous data to .tuerwache-previous-UUID, then activates the prepared directory. Activation failure rolls back the previous directory. Previous data is retained; remove it manually only after acceptance. Allow enough space for the archive, verification and working copies.

Clip paths are rewritten for DATA_DIRECTORY. AUTH_ENCRYPTION_KEY, if configured, must match the imported key. Browser/phone sessions must sign in again. Remote access stays off; retention, scheduled backups and Discord operations alerts are disabled for review before re-enabling.

Fresh Docker deployments use /app/data/state plus a separate backup volume. A volume root cannot be replaced: back up older /app/data installations before explicitly migrating to a data subdirectory. Run restore offline with the same mounts/environment. Pi migration transfers data, not platform-specific binaries. Large VLMs are best hosted on a separate machine.

Health and durable retries

Operations shows Ring/event connectivity, offline cameras, free space, slow jobs, delivery failures and the retry queue. Optional neutral Discord health alerts are throttled to every 30 minutes and disabled by default. Event silence is not an alarm by default; a quiet scene can be normal.

New failures in local AI, descriptions and uploads can be retried with durable bounded attempts. Paused cameras and removed local footage are skipped. Ambiguous Discord/push delivery is not automatically resent. Expo receipts confirm handoff to Apple/Google, not display to a person. Invalid device tokens are removed. A phone can trigger a test only for its own session.

AI quality

Review a clip description as correct/incorrect/uncertain, with an optional correction. Reviews belong to that description version and do not replace it. Under AI → AI quality, compare configured models using the same up to six frames. Cloud comparisons require explicit consent to transmit images, consume the daily limit and may incur fees. Comparisons send no notifications and preserve the original description. Comparison results can also be rated. No automatic training occurs.

Upgrade

Review changes, back up, stop, update source, rerun installer with appropriate AI option, start and verify a new audio/video event. Roll back old source and its matching data backup together. Never use one JSON store from multiple server processes.

Architecture and mobile apps

Ring camera → Ring cloud → Node server → clip → Python recognition → optional VLM → web/mobile/Discord. The camera does not expose a freely accessible local RTSP stream.

data/ is private JSON/file storage for one server process. Accounts protect private APIs/clips. Browser writes use CSRF; mobile sessions have separate revocable tokens. Model keys are not returned to apps/browsers.

Mobile status

Android: ARM64 test APK built on Windows, test-signed, not a Play Store release, not yet accepted on a physical phone. Server sign-in, clips, timeline and live integration are prepared. Verify actual build version: new web features are not automatically included in older APKs.

iOS: shared code exists, no signed installable build. Apple Developer access, signing and device/TestFlight tests remain. Real push needs Expo/Firebase/APNs projects, permissions and new builds. Installing the web app does not configure native push.

Phones need a reachable HTTPS address. On a phone, 127.0.0.1 refers to the phone itself. Ring credentials remain on the server. The Mobile app page shows available download/connection status.
